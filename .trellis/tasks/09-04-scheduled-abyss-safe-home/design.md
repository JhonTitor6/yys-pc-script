# 定时任务与狭间入口恢复设计

## 1. 设计结论

- 新增持久化的 `scheduled_tasks` 记录，作为“什么时候运行什么”的唯一事实源。
- 继续使用现有 `SchedulerService` 线程、`RunManager` 单运行槽和 `run_workflow_now()`；不引入第三方调度库。
- 工作流只保留“做什么”的定义；定时任务可引用工作流，也可直接保存一个脚本及其参数快照。
- 狭间暗域的未知画面 `ESC` 恢复保持为脚本专用逻辑，不改变通用 `EntryPreparer` 的未知画面零输入契约。

## 2. 分层与数据流

### 创建或编辑

1. GUI 根据目标类型展示脚本选择与参数表单，或工作流选择器。
2. GUI 提交执行目标、周期配置、补跑宽限期和启停状态。
3. API 在信任边界校验目标存在、周期字段完整、时间格式和星期范围。
4. `SchedulerService.calculate_next_run_at()` 使用提交配置和当前本地时间计算首个 `next_run_at`。
5. Repository 在一次事务中持久化任务和下一次运行时间。

### 到期执行

1. 调度线程读取已启用任务，按优先级降序、ID 升序处理。
2. 先比较 `next_run_at` 与任务宽限期，再检查单运行槽。
3. 脚本目标构造 `RunRequest`；工作流目标在启动瞬间一致读取最新工作流及有序步骤，形成含有效参数和失败策略的完整执行快照。
4. 成功取得执行槽后，在启动目标前提交本轮领取记录及执行快照；自动轮次的领取与清空本轮 `next_run_at` 在同一事务完成，提交失败不得启动目标。运行关联 `scheduled_task_id` 和独立 `occurrence_id`，供 REST、WebSocket、历史和 GUI 使用同一来源字段。
5. 完成、失败、过期或重启判定中断后，在同一事务保存轮次终态并更新任务状态与下一次时间；仅一次任务转为停用终态。手动轮次不修改自动计划。

## 3. SQLite 模型与迁移

新增 `scheduled_tasks` 表，保持字段最少且可直接查询：

| 字段 | 用途 |
|---|---|
| `id`, `name` | 稳定标识和用户名称 |
| `enabled` | 是否参与自动调度 |
| `target_type` | `script` 或 `workflow` |
| `script_id`, `workflow_id` | 二选一的执行目标；工作流外键使用 `ON DELETE RESTRICT` |
| `target_config_json` | 单脚本参数快照；工作流目标为空对象 |
| `schedule_type` | `interval`、`scheduled_time`、`weekly`、`once` |
| `schedule_config_json` | 各周期的最小配置 |
| `misfire_grace_seconds` | 补跑宽限期，默认 `1800` |
| `priority` | 保留现有确定性排序 |
| `next_run_at`, `last_run_at`, `last_status` | 可恢复调度状态与列表状态 |
| `legacy_workflow_id` | 旧工作流来源标识，非空时唯一；独立迁移完成标记防止删除后重建 |
| `created_at`, `updated_at` | 审计时间 |

新增 `scheduled_task_occurrences` 表，每轮使用独立主键 `id`，记录 `scheduled_task_id`、计划时间、触发来源、领取时间、状态、实际开始/结束时间和错误摘要。执行前先持久化领取状态，结束时更新同一行；过期轮次直接写终态。执行槽占用的重复轮询只发布当前状态，不创建 occurrence。自动轮次按任务和计划时间唯一，手动重跑每次使用新 ID，不覆盖原轮次。

该表增加可空 `target_snapshot_json` 保存当轮完整执行快照，与领取记录一同提交；未启动的过期或目标缺失轮次不伪造执行快照。运行开始后快照不可变，结果和进度通过关联 `runs` 表查询，不回写配置快照。

为 `runs` 幂等增加可空 `scheduled_task_id`、`occurrence_id`，并扩展 `RunRequest` 和运行快照。实际脚本运行继续写入现有 `runs`；同一工作流轮次的全部步骤和策略重试透传同一个 `occurrence_id`，手动重跑使用新轮次。不能仅通过任务 ID 推测某轮包含哪些运行。

建表和加列保持可重复执行；旧工作流数据复制与迁移完成标记在 `Database.initialize()` 的同一事务中提交：

- 复用现有 `app_settings` 表保存内部迁移完成标记 `scheduled_tasks_migration_v1`；该标记独立于定时任务记录，删除任务不会删除标记。
- 仅在完成标记不存在时，把旧 `trigger_type IN ('scheduled_time', 'interval')` 的工作流复制为工作流目标任务；全部复制成功后保存标记，失败则复制结果与标记一并回滚。
- 原样复制启停、优先级、触发配置、成功/失败间隔、有效的 `next_run_at` 和 `last_run_at`；间隔差异放入 `schedule_config_json`。
- 缺失 `next_run_at` 时，使用本次迁移统一的本地参考时间及共享纯时间函数，补齐严格晚于该参考时间的最近下一计划，不倒推或补跑过去的轮次。间隔任务的锚点细节随重点项 6 收敛，但结果必须是未来时间；停用任务仍保持停用。
- `legacy_workflow_id` 唯一约束防止同一旧工作流重复复制；完成标记存在后直接跳过数据复制，即使迁移出的任务已被删除也不得重建。（2026-09-05 用户确认）
- 不删除或改名旧工作流列；新调度器只读取 `scheduled_tasks`，避免双重触发。

## 4. 周期配置与纯计算

继续使用标准库 `datetime`，系统本地时间保持现有语义：

- `interval`：`interval_seconds`，并保留可选的成功/失败间隔。
- `scheduled_time`：零填充 `HH:MM`。
- `weekly`：零填充 `HH:MM` 和去重排序的 ISO 星期数组 `0..6`（周一到周日）。
- `once`：本地 `YYYY-MM-DDTHH:MM`，创建或重新启用时必须仍有可执行的未来时刻。

一个共享纯函数同时服务预览、保存和执行后推进。每日/每周取严格晚于参考时间的最近候选（恰好到点也排下一周期）；间隔沿用实际末次运行锚点；过期轮次从当前时间推进到下一未来周期，不补齐累计轮次。

补跑顺序固定：

1. `now - next_run_at > misfire_grace_seconds`：本轮过期。
2. 仍在宽限期但运行槽被占用：保持原 `next_run_at`，发布 `blocked_by_active_run`。
3. 槽释放且仍在宽限期：取得执行槽，原子保存本轮领取记录与清空本轮待执行时间；提交后才启动目标。
4. 运行完成后，原子提交轮次终态与下一周期或仅一次停用状态。

### 崩溃重启恢复（2026-09-05 用户确认）

- 恢复在调度线程启动前执行；尚无领取记录的自动轮次继续按原计划时间判断补跑宽限期。
- 已领取但无终态的轮次记为 `interrupted`，不自动重新启动目标；领取提交后、实际输入前崩溃也采用同一规则，不凭游戏画面猜测是否已经执行。
- 在同一事务中保存中断终态并恢复周期任务的下一计划；仅一次任务清空计划并停用。手动轮次中断不改变自动计划；间隔任务的时间锚点与跨周期推进规则仍按重点项 6 单独讨论。
- 已有终态及其计划推进结果保持不变。重复启动仅处理尚无终态的领取记录，不重复写中断历史或再次推进计划。
- 中断保留手动重跑入口。无法确定的实际开始/结束时间保留为空，恢复时间不得冒充实际结束时间。

## 5. API、运行和状态契约

新增最小 REST 契约：

- `GET /api/scheduled-tasks`
- `POST /api/scheduled-tasks`
- `PUT /api/scheduled-tasks/{id}`
- `DELETE /api/scheduled-tasks/{id}`
- `POST /api/scheduled-tasks/{id}/enable`
- `POST /api/scheduled-tasks/{id}/disable`
- `POST /api/scheduled-tasks/{id}/run-now`（所有任务均可立即运行；不改变自动计划，已结束的仅一次任务保持停用）
- `POST /api/scheduled-tasks/preview`
- `GET /api/scheduled-tasks/{id}/history`

API 返回规范化状态，不让前端从时间或日志猜测：`scheduled`、`blocked`、`running`、`success`、`error`、`expired`、`interrupted`、`target_missing`、`disabled`。`interrupted` 显示为“运行中断”。WebSocket `scheduler_status` 增加 `scheduled_task_id`、状态和 `next_run_at`，涉及具体轮次时带 `occurrence_id`，含义与 REST 一致。

`RunSourceType` 增加 `scheduled`，`RunRequest` 增加可空 `scheduled_task_id` 和 `occurrence_id`。工作流调度执行给每个实际脚本步骤及策略重试透传这两个 ID；手动运行普通脚本或普通工作流仍为空。所有定时任务的“立即运行”走相同目标执行函数但不改变自动计划；仅一次任务重跑后仍保持停用且不计算下一次时间。

删除工作流前先查询引用并返回 `409` 及可展示说明，SQLite 外键作为最终保护。脚本注册缺失不是异常输入尝试：调度器先把任务停用并持久化 `target_missing`，不调用 `RunManager.start()`。

### 工作流执行与历史快照（2026-09-05 用户确认）

- 快照保存工作流名称、工作流失败策略及全部有序步骤；每步保留来源步骤 ID、步骤类型、脚本目标、完整有效参数、条件、重试次数与步骤失败策略。读取工作流和步骤须处于同一一致性读取中，不能混入编辑前后的两个版本。
- 在轮次启动时按现有优先级合并默认配置、全局脚本配置和步骤参数，固定本轮有效参数；后续步骤与策略重试使用该快照，不重新合并变化后的全局配置。普通手动脚本的配置合并行为保持不变。
- 复用已有非外键 `runs.step_id` 标识快照中的来源步骤，和 `occurrence_id` 共同关联本轮步骤及其重试。`runs.workflow_step_id` 仅在来源步骤仍存在时保存，否则置空；该存在性处理必须在写入运行记录的同一数据库操作中完成，避免编辑删除引发外键竞态。共享执行路径保留原步骤参数、顺序和失败策略，不能因为来源步骤已删除而跳过本轮步骤。
- 调度历史及其关联运行详情从 `target_snapshot_json` 展示当轮工作流，不读取最新定义替代；快照包含未执行步骤，GUI 明确区分执行结果与未执行状态。旧历史没有快照时如实显示缺失，不用当前定义补造。
- 定时任务的下一轮和立即运行仍实时读取当时最新工作流，创建新快照；历史快照只用于该轮执行和复盘，不改变实时引用契约。

## 6. GUI 设计

- 一级导航增加“定时任务”；现有工作流页面移除调度、成功/失败间隔和启停控件。
- 定时任务页面复用工作流页面的 `list|editor` 子视图、dirty 离开保护、Toast 和通用表单字段渲染，不建立第二套弹窗框架。
- 目标类型切换为“单个脚本 / 工作流”。单脚本配置复用 `scriptSchema()`、`renderField()` 和现有规范化函数；工作流只显示选择器及实时引用说明。
- 周期控件按类型只显示所需字段：间隔秒数、每日时间、星期多选加时间、仅一次本地日期时间。时间输入初始为空，补跑宽限期初始为 30 分钟。
- 列表显示名称、目标、周期摘要、下一次运行、宽限期和后端状态；操作为立即运行、启停、编辑、删除。
- 工作流轮次的历史详情展示完整快照中的步骤、顺序、参数和失败策略，并关联实际运行与重试；未执行步骤单独标明，原定义编辑后仍展示当轮版本。
- 800×600 使用两行摘要并收起次要信息，不产生横向滚动；错误留在表单区域并通过可访问 Toast 提醒。

该导航变更会覆盖 `08-08-gui-modern-workbench` 和 `08-08-gui-secondary-views` 中“固定四个一级入口”的旧验收，实施时须同步更新对应回归预期，但不得顺带重做那些任务的其他页面。

## 7. 狭间暗域入口恢复

保持改动局部在狭间入口：

1. `on_run()` 识别当前场景。
2. 四个狭间区域或敌人选择页直接同步状态并返回。
3. `abyss_selection`、`daily` 等可验证中途页面复用现有入口步骤并跳过已经完成的前缀。
4. 其他已知页面先使用场景图中不绕首页的有效路径；没有路径或后置验证失败才进入首页恢复。
5. 首页恢复按可见 `to_home.bmp`、可见 `return.bmp`、逐次 `ESC` 的优先级执行。
6. 未知画面先重识别；无按钮后逐次发送 `ESC`。回首页按钮、返回按钮和 `ESC` 共享同一次入口准备的退层预算：合计最多 6 次，退层阶段累计最多 30 秒。每次输入后截图并重新判断首页、确认离开弹窗、战斗或可用捷径，不因识别结果变化或导航重试而重新初始化预算。
7. 确认离开弹窗出现后只再按一次 `ESC` 取消，并稳定验证首页；不得发送确认退出操作。
8. 战斗状态持续截图识别，进行中零输入；单独使用 180 秒单调时钟等待窗口，超时返回结构化“入口等待超时”，交给既定失败策略处理。每次轮询检查停止，重复命中战斗标记不得刷新截止时间。
9. 确认战斗结束页后，停止战斗等待计时，按已验证模板或继续提示的位置主动点击关闭；点击后刷新截图，若仍有已确认结算页则逐页处理，离开结算后回到步骤 1。启动时直接命中结算也走此分支，不进入空等待。

### 首页恢复的统一退层预算（2026-09-05 用户确认）

- 回首页按钮、返回按钮和 `ESC` 每执行一次退层都消耗一次预算，按钮点击失败或画面未变化也不返还次数；没有发送输入的截图和识别不消耗动作次数，但消耗退层阶段时间。
- 战斗等待、结算关闭暂停退层计时但不重置已用预算；返回首页恢复时续用剩余次数与剩余耗时。结算关闭和退出弹窗取消使用独立保护，不与退层动作混计。
- 每次退层后先获取新截图判断首页/退出弹窗，再决定是否还有下一次退层预算，避免第 6 次已经到达首页仍被误判失败。退出弹窗只允许既定的一次取消 `ESC`，该动作不占退层次数；全局动作预算应预留取消需要，不绕过全局保险丝或停止信号。

### 战斗结束页的主动处理（2026-09-05 用户纠正并确认）

- 复用 `EntryPreparer._step_waiting_battle()` 的 BATTLE/SETTLEMENT 分流和 `_dismiss_settlement()` 的已验证模板点击模式；狭间专用入口配置真实画面支持的结算证据，不放宽通用未知画面零输入规则。
- 结算识别与可点击位置必须来自当前截图；只处理已确认的胜利、失败、奖励或继续页，不因战斗标记暂时消失就发送点击或 `ESC`。
- 不直接调用会增加胜利/战斗次数的 `_on_battle_victory()`、`_on_battle_end()`，也不直接复用固定坐标的 `_on_ocr_click_screen_continue()`；入口只关闭此前战斗的结算页，不污染本轮统计。
- 结算每次点击前检查停止和动作预算，点击后重新截图并验证，不根据旧截图连续发送输入。关闭失败或后置场景不明不得伪报入口成功；结算关闭的独立次数与耗时上限继续在重点项 4 收敛。
- 180 秒只限定入口阶段等待当前战斗结束，不用于正常业务挂机。所有首页恢复退层统一使用上述 6 次/30 秒要求，真实启动路径如何接入停止与保险丝继续在重点项 4 收敛。

新增狭间专用“确认离开”识别模板或等价的已验证识别证据，并用用户确认的真实帧制作最小回放夹具。不得覆盖当前用户已修改的 `yys/common/images/scene/home.bmp`。

所有点击、拖拽和按键继续通过已注入环境的 Mouse/Keyboard controller 或直接 `GameEnvironment`；禁止新增原生 Win32 输入旁路。

## 8. 错误与可观测性

- API 校验错误返回 `400`，目标不存在返回 `404`，工作流被引用返回 `409`。
- 调度错误使用稳定状态/错误码区分：配置非法、目标缺失、过期、活动运行阻塞和目标执行失败。
- 狭间恢复失败至少记录最终场景证据、动作次数、耗时和结构化入口错误；不得伪造截图路径。
- 前端只消费规范化状态和可用操作；刷新或 WebSocket 重连从 REST 快照恢复。

## 9. 回滚边界

- 数据库只做加表、加列和复制，不删除旧列；回滚旧版本仍能读取原工作流与运行历史。
- 先完成迁移、后端读写和调度测试，再切换 GUI；后端未就绪时不移除旧 GUI 字段。
- 狭间恢复与定时任务可分开回滚，二者只通过正常 `RunRequest` 相接。
- 保留无关工作树修改，尤其是 `gui/installer.nsh` 与 `yys/common/images/scene/home.bmp`。
