# 工作流串联每日一条龙

## 目标与需求

复用现有工作流，按收菜、寄养、逢魔、地域鬼王、御魂、活跃度领奖顺序串联；依赖六个独立脚本均完成验收，失败或用户停止不继续。

## 验收

- [ ] 可单独运行（业务脚本）或按六步顺序可靠推进（工作流）。
- [ ] 完成判定来自真实页面；未知、失败及停止不误记成功。
- [ ] 保留现有脚本行为与离线验证证据，未验证项明确记录。

## 依赖

归属 `10-17-daily-routine`；本轮串联保护与配置草案已进入实施，完整六步联调仍依赖各业务脚本及素材。

## 已发现的串联前置问题

已复现并修复：`SchedulerService._run_step_with_policy` 曾把非 error 的状态一律当成功，导致 stopped 或仍运行的步骤推进后续业务。现在只有明确 success 或本次调度器实际发出的限时停止才成功；用户停止中断，skipped 与 manual 分别处理，未完成或未知状态拒绝推进。

## 本轮实施范围

- 2026-10-18 用户明确授权进行实机验证；先接入三项已完成的独立模块、离线回归，再使用带精确确认短语、前台截图、动作／超时预算和 F12 急停的单次执行入口验证。该授权覆盖本次实机动作及必要的局部修复，不包含 Git 提交、推送或归档。
- 单人魂土先以 1 场冒烟验证入口、结算和回庭院，脚本默认仍为用户确认的 10 次可配置；已有当日任务／领奖完成状态只验证和记录，不重复消耗。逢魔非开放时段不声称完成战斗实测。
- 受保护 CLI 新增六个一条龙脚本中的可执行 ID；`--max-battles` 仅影响结界突破及新单人魂土分支，默认分别为 9／10，其他脚本忽略；`--skip-quit-three` 仍只影响结界突破，旧精确确认、观察零输入、前台执行和不自动重启行为不变。
- 用户已授权开始实施并要求继续；先完善串联执行语义和六步配置草案，不启动真实游戏或写入用户工作流数据库。
- 普通步骤用户停止后，不论失败策略是停止、继续或重试，都不得启动后续步骤。
- 缺失、非终态运行状态及等待未完成都不能当成功；明确跳过保留“跳过”语义，不能当作任务已完成。
- 实际开始第一步前校验生产注册表中全部脚本存在，避免先消耗资源、到后续缺失脚本才失败。
- 六步配置草案默认禁用、手动触发；包含尚待素材实现的步骤，不注册虚假占位脚本。

## 旧行为保持的原子断言

- 实机发现底部卷轴菜单与旧右侧箭头同时存在：仅在已确认庭院分支优先点击已匹配的新底部卷轴；原旧菜单变体、`home_verified=False` 的严格拒绝和分组／阵容参数作用域保持不变。活跃领奖只以实际花合战菜单项确认展开，不把其他箭头命中当菜单已展开。
- 当前樱花庭院旧场景标记分数不足：追加既有录制的探索灯笼为 home 变体，不替换旧标记、不降低旧阈值。单人魂土从客户区全图查找该变体并点击实际命中位置，原组队入口和已有场景 ID 保持不变。
- `run_step(workflow_id, step)` 继续返回运行 ID 或 None；外部调用无需改参数。
- 成功步骤保持按顺序等待完成再推进；error 的 stop／continue／skip／retry 策略保持有效。
- manual 仍中断后续步骤；不会自动重试人工接管的运行。
- `run_until_time` 由调度器实际发出的按时停止仍视为该限时步骤正常完成；用户提前停止限时步骤不推进。
- 已有工作流时间计算、优先级、存储结构和原有配置不变。
