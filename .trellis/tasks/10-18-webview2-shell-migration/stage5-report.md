## 已复现的失败与契约差异

### F1：迁移发布时可能覆盖并发建出的目标库

- 对应 AC25，优先级 P1。
- 位置：`ui_backend/storage/workbench_db.py` 的 `migrate_legacy_database`。
- 触发：入口检查时目标不存在；一致性复制完成、发布之前，另一个进程创建了有效目标库。
- 复现：源标记 `old-source`；在发布前注入有效目标标记 `new-concurrent-data`。函数返回 `migrated`，最终目标标记变回 `old-source`。
- 根因：仅入口执行 `target.exists()`，最后 `os.replace(staging, target)` 允许覆盖；共用 `.migrating` 文件名也不提供并发隔离。
- 影响：违反“不覆盖已有目标”和设计要求的“并发冲突停止导入”，可能丢失新记录。
- 修复方向：每次使用独立临时副本，并用不覆盖目标的原子发布操作；冲突要明确报错。不是再加一次 exists 检查。

### F2：便携包只检查两个 EXE，可能继续使用旧或不完整载荷

- 对应 AC23，优先级 P1。
- 位置：`scripts/portable.nsi` 的 `check_backend` / `launch` 分支。
- 复现一：先运行 1.0.0 旧载荷，再运行版本号仍为 1.0.0 的新载荷，实际启动标记仍为 `old-build`，未使用新包中的 `new-build`。
- 复现二：删除缓存的 `backend/_internal/required.bin`，保留两个 EXE，再启动也没有恢复缺失文件。
- 正样本：首次解压、版本号升到 1.0.1 后使用新载荷、隔离永久数据哨兵保留，均通过。
- 根因：只凭版本号目录及两个文件的存在跳过整个解压；当前发布版本固定 1.0.0，同版本修复包尤其容易命中。
- 修复方向：载荷缓存需要区分实际构建并识别不完整解压；不能把“两个 EXE 存在”当作完整性证明。
- 边界：本项用真实 NSIS 逻辑与最小替身复现；尚未做完整正式便携包升级/并发运行的端到端检查。

### F3：后端访问日志包含完整鉴权 token

- 对应设计中的“日志不得泄漏 token”，优先级 P2。
- 位置：`ui_backend/main.py` 的 Uvicorn 默认日志，及 Rust 将 stdout/stderr 追加到永久 `logs/backend.log` 的链路。
- 复现：真实发行后端处理 `/ws/events?token=...` 后，日志中可检索到本次生成的完整 token。
- 影响：复制或分享后端日志可能连带暴露当次宿主的鉴权信息；不表示远程攻击者已获得访问权限。
- 本轮生成的验收日志已脱敏，报告和 JSON 只记录布尔结果，不保存 token 值；未改写真实用户日志。
- 修复方向：日志输出前脱敏 query token，覆盖 HTTP 图片 URL 与 WebSocket 日志，不改变现有 token 传输契约。

### D1：HTTP 来源拒绝的验收措辞与现有 CORS 语义不同

- 对应 AC21，按字面标准尚不通过。
- 复现：携带正确 token、`Origin: http://evil.example` 的 `/api/scripts` 请求返回 200，但没有 `Access-Control-Allow-Origin`。
- 这证明浏览器 CORS 不放行读取，不能写成“服务端拒绝了请求”，也不能据此推断不带 token 可越权。
- 若要求服务端严格拒绝未知 Origin，需要补充拒绝逻辑及原调用方兼容测试；若原意仅为 CORS，需要先明确验收契约，不能静默把 200 记作严格拒绝通过。
