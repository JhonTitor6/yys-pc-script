# 通用入口与恢复运行时

## Goal

让用户从受支持的任意游戏页面启动脚本时，系统能够先理解当前画面、处理安全的准备动作、等待不可中断状态结束，并可靠导航到脚本入口；无法安全恢复时必须保留证据并转入人工接管，不能盲点恢复或把入口失败误报为成功。

## Background

当前入口机制由业务脚本在主循环前直接调用 `SceneManager.goto_scene(entry_scene)`。它只能从单个已识别场景计算 BFS 路径；当前画面未知、处于战斗、存在弹窗，或场景图节点命名漂移时都会直接失败。

## Confirmed Facts

- `yys/common/scene_manager.py:114` 以场景图片文件名注册场景，以跳转按钮文件名解析边；`detect_current_scene()` 只返回首个命中场景，未知时返回 `None`。
- `yys/common/scene_manager.py:283` 的 `goto_scene()` 要求首次截图已经能识别当前场景；每条边固定等待后只进行有限确认，失败即返回 `False`。
- 当前公共场景目录注册 `battling`、`exploration_chapter_28`、`soul_selection`，而跳转文件推导出 `battle`、`chapter_28`、`soul`，图中存在未注册目标节点。
- `yys/common/event_script_base.py:404` 在 `entry_scene` 跳转失败时正常 `return`，不会进入业务主循环。
- `ui_backend/runs/manager.py:39` 在线程启动前就把运行状态写为 `running/script_running`；`ui_backend/runs/manager.py:304` 将没有抛异常的 `script.run()` 返回视为可成功完成。因此入口跳转失败目前可能被误报为成功，而不是结构化启动失败。
- `win_util/environment/guarded.py` 与 `win_util/event.py:229` 已提供运行超时、动作上限、连续未知画面和紧急停止能力，但这些保险丝只在事件主循环中生效，尚未覆盖入口准备阶段。
- `tests/common/test_scene_transition_entry.py` 已锁定三个现有入口：探索 `exploration_chapter_28`、结界突破 `barrier_breakthrough`、御魂 `soul_selection`；狭间暗域当前明确不启用统一入口。
- 现有工作台要求手动执行和编排执行都经过 `RunManager`，并保持单执行槽、规范化运行快照、结构化失败证据以及状态驱动的可用操作。

## Requirements

### R1. 规范化场景身份与图完整性

- 公共运行时必须使用唯一、稳定的场景标识；文件名解析不得继续静默制造未注册的源节点或目标节点。
- 构建场景图时必须校验所有显式边和通用边，发现未知节点应在启动前给出可定位错误。
- 迁移期间如需兼容旧名称，别名必须显式声明并归一化，不能由业务脚本自行猜测。

### R2. 入口准备与状态理解

- 业务脚本只声明入口需求和恢复策略，不自行实现“从任意页面回入口”的流程。
- 启动阶段必须区分基础场景、覆盖层/弹窗、战斗或过渡模式、识别证据与稳定性；不能只依赖一个可空字符串。
- 只有在目标入口被连续或等价地验证为稳定后，才进入业务主循环并把阶段切换为真正运行中。

### R3. 战斗中的安全等待

- 检测到战斗进行中时进入可观察的等待安全入口阶段，不主动点击退出战斗。
- 等待期间允许处理已确认安全的战斗结算动作，但不得执行会中止战斗或消耗不可逆资源的动作。
- 单次战斗安全等待窗口为 3 分钟；超时后提供继续等待、转人工接管和停止能力。
- 用户每次选择“继续等待”会新增一个 3 分钟等待窗口，并允许重复选择；每次延长必须记录为运行事件。
- 延长等待只延长战斗阶段截止时间，不得停用紧急停止、状态异常检测、动作预算或证据记录。

### R4. 安全恢复阶梯

- 恢复顺序从低风险到高风险：重新识别、关闭已知安全弹窗、等待过渡/战斗结束、重试已确认动作、返回上一层、返回主页、人工接管、停止并导出证据。
- 每一步必须有前置条件、动作、后置条件、超时与重试上限；后置条件未验证时不得继续下一跳。
- 未知画面必须安全失败；禁止无模板、无坐标语义或无结果验证的盲点点击。
- 入口准备阶段只自动处理已确认的公共战斗结算画面；该结算发生在新业务运行之前，不得增加御魂脚本的战斗次数或胜利次数。
- 悬赏封印仅在现有配置明确为“拒绝”时自动点击已确认的拒绝按钮；接受全部、仅接受勾协等会改变后续流程的策略在入口准备阶段转入人工接管。
- OCR“点击屏幕继续”、业务模块私有弹窗以及任何未知弹窗均不纳入首个 MVP 的自动处理范围。

### R5. 运行阶段与可观察性

- 至少能够区分排队、准备、等待安全入口、导航、业务运行、暂停以及成功、失败、停止、人工接管等终态。
- REST、WebSocket、持久化快照和 GUI 必须共享同一规范化阶段与可用操作，不得由日志文本推断状态。
- 入口识别、等待、导航或验证失败必须产生稳定错误码、可读原因、最后识别证据和真实截图；截图失败必须显式记录捕获错误。
- 入口失败不得被记录为业务成功，业务运行阶段不得在入口准备完成前出现。
- 进入人工接管时，当前 run 终结为 `manual` 并释放执行槽；不得保留可继续发送输入的旧线程或旧导航上下文。
- 用户处理后选择“重新识别并重试”时创建关联的新 run；新 run 从新截图和状态解析开始，不复用旧场景快照、旧路径或旧动作游标。
- 新 run 必须保留原 run 的关联标识、任务/工作流上下文、重试次数和证据跳转能力。

### R6. 安全边界与统一执行路径

- 手动启动与工作流启动必须经过同一入口准备流程。
- 入口准备期间的所有鼠标和键盘输入必须经过注入的 `GameEnvironment`，并计入动作预算。
- 总超时、动作上限、连续未知画面和紧急停止在准备、导航和业务运行阶段都必须保持有效。
- 一次运行不得自动启动另一次运行，且不得破坏现有单执行槽约束。

### R7. 兼容与分阶段交付

- 现有 `entry_scene` 为空的旧脚本继续按原有方式运行，除非后续明确纳入迁移范围。
- 已能从受支持场景成功进入探索、结界突破和御魂的现有路径不得退化。
- 现有暂停、恢复、停止、失败恢复、状态快照和工作流失败策略不得改变既有语义。
- 首个 MVP 只以御魂 `soul_raid` 完成端到端闭环；探索与结界突破本次只做既有行为回归，不迁移到新入口准备流程。
- 公共契约必须允许后续逐个迁移探索与结界突破，而不是为御魂写不可复用的特例或重写全部业务脚本。

## Acceptance Criteria

- [ ] AC1：场景图初始化会拒绝或显式归一化 `battle`、`chapter_28`、`soul` 等未注册节点，不再生成幽灵路径。
- [ ] AC2：从已支持的稳定页面启动试点脚本，运行依次经过准备、导航、入口稳定验证、业务运行；业务运行状态不会提前出现。
- [ ] AC3：从真实或确认回放的战斗早期、中期、晚期启动试点脚本，系统不发送中止战斗输入，能够等待结算并继续进入目标入口。
- [ ] AC4：战斗等待达到 3 分钟时，运行提供继续等待、转人工接管或停止；每次继续只延长 3 分钟并产生审计事件，持续未知画面仍按异常处理。
- [ ] AC5：启动前战斗结算可被关闭且不改变御魂业务计数；配置为拒绝时悬赏封印可被拒绝；接受类策略、OCR“点击屏幕继续”、业务私有弹窗和未知弹窗均不会触发盲点恢复。
- [ ] AC6：每条导航动作只有在后置场景验证成功后才推进；失败会在有界重试后升级恢复，不会无限循环。
- [ ] AC7：入口跳转失败不会进入业务主循环，也不会被 RunManager 记录为成功。
- [ ] AC8：手动启动与工作流启动产生相同的准备阶段、导航行为和失败语义。
- [ ] AC9：准备阶段的输入经过 `GameEnvironment` 并受超时、动作上限、未知画面限制和紧急停止保护。
- [ ] AC10：`entry_scene` 为空的旧脚本、现有单执行槽、暂停/恢复/停止、运行快照和工作流失败策略均通过回归测试。
- [ ] AC11：御魂 `soul_raid` 至少具有一条基于确认真实帧的端到端回放测试，覆盖稳定页面启动、战斗中启动和未知画面安全失败；探索与结界突破的既有入口回归保持通过。
- [ ] AC12：转人工接管会终结当前 run、释放执行槽并停止所有自动输入；“重新识别并重试”创建关联新 run，保留来源关系但不复用旧导航状态。
- [ ] AC13：工作流中的关联重试仍归属于原工作流步骤；原 `manual` run 保持不可变，新 run 独立记录最终结果，后续步骤只在新 run 成功后推进。

## Out of Scope

- 整体迁移 OnmyojiAutoScript 或 Whimbox 的技术栈。
- 一次性重写全部业务脚本或为所有游戏页面补齐识别模板。
- 默认主动退出、投降或中止正在进行的战斗。
- 对未知画面进行未经验证的坐标点击、连续按键或无限重试。
- 在本规划获得用户审阅并执行 `task.py start` 前修改业务代码。
