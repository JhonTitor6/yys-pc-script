# 两个外部项目学习结论与目标项目设计建议

> 研究日期：2026-08-08  
> 研究对象：[OnmyojiAutoScript](https://github.com/runhey/OnmyojiAutoScript) 与 [Whimbox](https://github.com/nikkigallery/Whimbox)  
> 目标项目：yys-pc-script  
> 文档性质：外部项目学习、目标项目架构与 GUI 改进建议，不直接替代实现规格。

## 1. 结论摘要

本次学习的核心结论是：目标项目不需要整体迁移到任一外部项目的技术栈，而应保留现有 Python、事件驱动、图像识别和 FastAPI/WebSocket 基础，吸收两类成熟经验。

- 从 OnmyojiAutoScript 学习“自动化运行时”：统一的任务生命周期、原子动作契约、调度优先级、失败恢复、运行证据和人工接管。
- 从 Whimbox 学习“产品工作台”：清晰的信息架构、页面级任务入口、配置与运行状态分离、非阻塞进度反馈、通知抽屉和可复用配置表单。
- 对目标项目的优先级应是先提升“可观察、可恢复、可解释”，再扩展复杂 GUI 能力；否则 GUI 只能把现有运行时的不确定性包装起来。
- 近期目标形态应是“任务工作台”，而不是聊天窗口或单纯脚本列表：用户可以发现任务、配置任务、启动任务、观察阶段、处理失败并复盘运行记录。

建议的总体路线：

~~~text
现有脚本能力
    ↓ 统一配置与运行契约
任务注册中心 → 工作流/调度服务 → 单任务运行槽位
    ↓                         ↓
运行状态与事件总线       截图、OCR、动作、日志证据
    ↓                         ↓
FastAPI + WebSocket ← Electron/浏览器 GUI 工作台
~~~

## 2. 目标项目当前基线

### 2.1 已有基础

目标项目已经具备以下可复用基础：

| 领域 | 当前能力 | 判断 |
| --- | --- | --- |
| 自动化执行 | Python 业务脚本、事件驱动基类、图像识别、OCR、鼠标键盘控制 | 是核心资产，应继续保留 |
| 场景理解 | yys/common/scene_manager.py 已有场景检测、场景图和路径搜索能力 | 可作为统一场景层的基础 |
| 后端 | ui_backend/app.py 提供 FastAPI 应用工厂、脚本/配置/运行/工作流接口 | 已具备工作台后端雏形 |
| 运行管理 | ui_backend/runs/manager.py 已有单执行槽位、暂停/恢复/停止、日志接入和状态快照 | 需要补充明确状态机和证据模型 |
| 工作流 | ui_backend/scheduler/service.py 支持立即运行、步骤运行、等待时间和运行至指定时间 | 当前更像工作流执行器，周期调度和失败策略尚未完整实现 |
| GUI | gui/index.html、gui/renderer.js、gui/styles.css 已形成深色工作台布局 | 视觉方向可延续，信息架构和组件边界需要收敛 |

### 2.2 当前主要缺口

1. 运行状态、脚本阶段、工作流步骤和进程状态尚未形成一套稳定的状态模型。
2. 后端接口大量使用原始字典，状态字段和错误语义容易随着功能增加而漂移。
3. 运行日志能展示过程，但截图、OCR 结果、动作和异常之间缺少关联，失败后难以复盘。
4. 调度服务已经有运行入口，但失败策略、重试、跳过、继续和周期调度尚未落成统一规则。
5. 当前 GUI 已有导航和信息卡片，但“启动前配置—运行中观察—失败后处理”的主流程还不够连贯。
6. gui/package.json 目前主要只有启动、开发和构建脚本，缺少前端 lint、类型检查和组件级测试门槛。

### 3.1 值得学习的事实

#### A. 任务生命周期比单个脚本函数更重要

OnmyojiAutoScript 把脚本运行包装成可管理的任务对象，任务具有配置、启动、暂停、收尾、成功/失败间隔和下一次运行时间等生命周期信息。调度器面向任务运行，而不是直接调用任意函数。

这对目标项目的启示是：每个可执行脚本都应有稳定的运行契约，至少能够回答以下问题：

- 当前运行的是哪个任务、哪个工作流和哪一步。
- 任务处于等待、运行、暂停、停止、成功还是失败。
- 失败是否可重试，重试次数和下一次重试时间是什么。
- 任务是否需要人工接管，以及用户接管后如何继续。
- 运行结束后留下哪些截图、日志和配置快照。

#### B. 原子动作有统一的等待和失败语义

OnmyojiAutoScript 的图像原子动作不是简单的“找到图片就点击”，而是把出现、等待、点击、长按、滑动、OCR 等动作封装成可复用规则，并让超时和失败成为动作的一部分。

目标项目可以提炼出类似的最小契约：

~~~python
class ActionResult:
    success: bool
    action_name: str
    elapsed_ms: int
    evidence_id: str | None
    error_code: str | None

def wait_until_appear(target: str, timeout: float) -> ActionResult:
    ...

def appear_then_click(target: str, timeout: float) -> ActionResult:
    ...
~~~

这里的重点不是复制类名，而是统一动作的输入、超时、结果、证据和错误码。脚本层只负责业务意图，底层负责识别和操作细节。

#### C. 调度器需要面向失败设计

参考项目的调度模型包含任务启用状态、优先级、下一次运行时间、成功/失败后的间隔以及运行期间的调度控制。它还提供任务重试、人工接管、回到主页、热身和关闭游戏等运行策略。

目标项目当前的工作流服务中，失败策略仍未完整实现，异常通常会终止工作流。因此应把以下策略变成显式配置，而不是散落在业务脚本中：

| 策略 | 适用场景 | 默认建议 |
| --- | --- | --- |
| retry | 网络抖动、界面短暂未出现 | 有上限地重试，指数退避 |
| skip | 可选步骤或非关键奖励领取 | 记录原因后继续 |
| stop | 核心页面、账号或战斗状态异常 | 立即停止并保留证据 |
| manual | 需要用户确认或游戏状态不确定 | 暂停并提供接管入口 |

#### D. 运行证据是自动化产品的一部分

参考项目的运行体验不仅显示日志，还提供当前截图、脚本上下文、状态和调试入口。对于图像识别类自动化，失败时的截图比一句“找不到按钮”更有价值。

目标项目建议建立一次运行的证据链：

~~~text
运行 Run
 ├─ 配置快照 ConfigSnapshot
 ├─ 状态事件 StateEvent
 ├─ 原子动作 ActionEvent
 ├─ OCR/识别结果 RecognitionEvent
 ├─ 截图 Screenshot
 ├─ 日志 LogRecord
 └─ 异常 ErrorRecord
~~~

每类证据至少带有 run_id、step_id、时间戳和序号。这样 GUI 才能从一个失败步骤跳转到对应截图、日志和动作，而不是让用户在整段文本中搜索。

### 3.2 对目标项目的直接映射

| 外部经验 | 目标项目落点 | 近期实现方式 |
| --- | --- | --- |
| 任务对象与生命周期 | ui_backend/runs/manager.py、脚本基类 | 抽出统一 RunState、TaskState、StepState，API 和 WebSocket 只传稳定枚举 |
| 原子图像动作 | yys/common 及各业务模块 | 逐步将等待、识别、点击、超时和证据写入统一动作结果 |
| 调度优先级与间隔 | ui_backend/scheduler/service.py | 先实现失败策略与重试，再补真正的周期调度循环 |
| 运行截图与调试 | ui_backend/runs、GUI 右侧栏 | 先保留最近截图和失败截图，再增加动作时间线与 OCR 详情 |
| 人工接管 | 运行控制 API 与主工作区 | 失败状态显示“暂停原因、建议操作、继续/停止”三件套 |

### 3.3 不宜直接照搬的部分

- 不迁移 Android、ADB、uiautomator2、scrcpy 等设备层；目标项目面对的是 PC 游戏窗口，设备抽象会增加无关复杂度。
- 不为追求界面相似而迁移 PySide/QML/Fluent UI；目标项目当前 GUI 已经是 Electron/Web 工作台，优先收敛现有方案。
- 不直接复制外部项目图片、图标、字体和业务资源；使用前需要单独确认许可证和再分发边界。
- README 对 GUI 技术的描述与当前源码实现存在差异，学习时以当前源码和实际运行行为为准，不以单一文档描述做架构决策。

### 4.1 值得学习的事实

#### A. 前后端边界清晰

Whimbox 主仓库明确将后端与 UI 分离，桌面 UI 位于独立的 whimbox_app 仓库。桌面端通过 Electron 主进程连接后端，并把连接状态、任务状态和页面状态显式化。

目标项目不一定要拆成两个仓库，但应保留同样清晰的边界：

- Python 后端负责业务、调度、运行状态和证据。
- GUI 负责导航、配置编辑、状态呈现和用户操作。
- WebSocket 负责实时事件，HTTP 负责查询和命令。
- GUI 不直接读取脚本内部变量，也不通过解析日志猜测运行状态。

#### B. 信息架构围绕用户任务组织

Whimbox 的页面通常有左侧分组导航、页面标题与说明、主操作按钮、任务配置和状态反馈。导航不是按代码模块罗列，而是按用户想完成的事情组织。

这对目标项目的启示是：GUI 导航应以“运行、编排、历史、工具、设置”组织，而不是把每个 Python 模块直接暴露给用户。

#### C. 连接、任务和进度都有明确状态

外部 UI 对后端连接使用 idle、connecting、open、closed、error 等状态，对任务使用 started、stopping、completed、cancelled、error 等阶段。按钮和页面内容随状态改变，而不是始终显示一个“开始”按钮。

目标项目应统一这三类状态：

~~~text
连接状态：未连接 → 连接中 → 已连接 → 断开/错误
运行状态：空闲 → 启动中 → 运行中 → 暂停/停止中 → 成功/失败/取消
工作流步骤：待执行 → 执行中 → 重试中 → 跳过/成功/失败/人工接管
~~~

#### D. 长任务与短操作分开反馈

Whimbox 对短时操作使用进度弹窗，对长时间运行使用页面内状态和通知，不让一个全屏模态框阻塞整个应用。通知抽屉承载历史消息，进度组件承载当前操作，两者职责不同。

目标项目可以将“当前运行”固定在主工作区，将“历史通知”放入抽屉，将“危险操作确认”保留为模态框。这样用户可以在任务运行期间查看日志、切换页面或调整下一次任务，而不丢失运行上下文。

### 4.2 对目标项目的直接映射

| Whimbox 经验 | 目标项目设计 | 价值 |
| --- | --- | --- |
| 分组侧边栏与二级导航 | 一级：运行、工作流、历史、工具、设置；二级：具体任务或功能 | 降低脚本数量增加后的导航混乱 |
| 页面标题、描述和主操作 | 每个页面首屏解释用途，并提供唯一主操作 | 用户知道当前页面要做什么 |
| 连接状态显式化 | 顶部显示后端连接、WebSocket 和游戏窗口状态 | 避免用户把后端断开误认为脚本失败 |
| 可复用配置字段 | 根据脚本注册信息生成表单，字段带类型、默认值、范围和说明 | 减少手写表单和配置漂移 |
| 进度弹窗与通知抽屉分离 | 当前进度放主工作区，历史消息放通知抽屉 | 长任务不阻塞，事件仍可追踪 |
| 组件化页面 | 把导航、配置、运行卡片、日志、截图、确认框拆为可复用组件 | 便于增加任务而不复制整页 HTML |

### 4.3 不宜直接照搬的部分

- 不把 AI 聊天作为目标项目的主入口；本项目的核心价值是稳定执行和可解释运行，聊天不能替代任务状态与日志。
- 不照搬 Whimbox 的粉色暖色视觉、订阅、微信或视频悬浮等业务元素；视觉应服务于游戏自动化工作台。
- 不为了复刻页面而强行迁移 React/Tailwind；如果继续使用现有 Electron/Web 技术，应先建立组件边界和状态契约，再考虑框架升级。
- 不把聊天消息当作运行日志来源；日志、事件、通知和用户对话应保持不同数据模型。

## 5. 目标项目设计

### 5.1 目标形态

目标项目的 GUI 应成为一个“可观测的自动化任务工作台”，核心闭环如下：

~~~text
选择任务
  ↓
查看默认配置与预计影响
  ↓
调整配置并保存配置快照
  ↓
启动任务/工作流
  ↓
观察阶段、进度、截图、日志和识别结果
  ↓
成功完成，或进入重试、跳过、人工接管、停止
  ↓
在历史中复盘本次运行
~~~

### 5.2 推荐架构

~~~mermaid
flowchart LR
    GUI["Electron 工作台"] -->|"HTTP / WebSocket"| API["FastAPI 应用层"]
    API --> Registry["任务注册中心"]
    API --> Scheduler["工作流与调度服务"]
    Scheduler --> RunManager["运行管理器"]
    RunManager --> Script["业务脚本 / 事件驱动基类"]
    Script --> Scene["场景管理与识别"]
    Script --> Action["统一原子动作"]
    Action --> Device["PC 截图与输入设备"]
    RunManager --> EventBus["运行事件总线"]
    EventBus --> Evidence["日志 / 截图 / OCR / 动作证据"]
    EventBus --> GUI
~~~

### 5.3 后端设计原则

#### 原则一：配置、命令、状态、事件分离

建议明确区分四类数据：

| 数据 | 说明 | 例子 |
| --- | --- | --- |
| 配置 Config | 用户希望任务如何运行 | 战斗次数、式神、等待时间 |
| 命令 Command | 用户对运行实例发出的操作 | 启动、暂停、恢复、停止、重试 |
| 状态 State | 系统当前事实 | 当前阶段、进度、错误码、可用操作 |
| 事件 Event | 状态变化及过程记录 | 步骤开始、截图产生、识别失败、重试 |

GUI 根据状态决定按钮和视觉，不根据日志文本推断状态。事件用于实时更新和历史复盘，状态用于刷新页面和恢复连接后的快照。

#### 原则二：统一运行快照

建议所有运行接口返回同一类结构，字段至少包括：

~~~json
{
  "run_id": "run-20260808-001",
  "task_id": "soul_raid",
  "workflow_id": "daily",
  "status": "running",
  "step_id": "battle",
  "step_status": "executing",
  "progress": {"current": 3, "total": 10},
  "started_at": "2026-08-08T10:00:00+08:00",
  "last_event_at": "2026-08-08T10:01:20+08:00",
  "error": null,
  "available_actions": ["pause", "stop"]
}
~~~

这类结构不要求一次性改完所有接口，但新接口应优先遵循它，旧接口逐步兼容迁移。

#### 原则三：失败必须可解释

失败响应至少应包含：

- 稳定错误码，而不是只返回异常字符串。
- 发生失败的任务、步骤和原子动作。
- 最后一次识别目标、超时和重试次数。
- 关联的截图或证据 ID。
- 用户可以执行的下一步：重试、跳过、人工接管或停止。

### 5.4 工作流语义

工作流步骤建议使用显式结构，而不是在 GUI 中拼接任意函数调用：

~~~yaml
id: daily
name: 日常任务
steps:
  - id: prepare
    task: open_game
    on_failure: stop
  - id: soul_raid
    task: soul_raid
    on_failure: retry
    retry:
      max_attempts: 2
      backoff_seconds: 5
  - id: reward
    task: collect_reward
    on_failure: skip
~~~

最低可用语义应包括：

- 顺序执行和步骤状态。
- retry、skip、stop、manual 四类失败策略。
- 每个步骤独立的超时和重试上限。
- 工作流取消时对当前脚本的安全停止。
- 运行结束时输出汇总结果和失败步骤列表。

周期调度可放在后续阶段实现，但模型应预留启用、优先级、下一次运行时间、成功间隔和失败间隔字段。

### 5.5 GUI 信息架构

| 一级页面 | 主要内容 | 主操作 |
| --- | --- | --- |
| 运行 | 当前运行、任务选择、配置摘要、阶段进度、日志和截图 | 启动 / 暂停 / 恢复 / 停止 |
| 工作流 | 工作流列表、步骤顺序、失败策略、预计耗时 | 新建 / 编辑 / 立即运行 |
| 历史 | 运行记录、成功率、耗时、失败原因、证据入口 | 查看详情 / 重试 |
| 工具 | 截图查看、OCR/图像定位、ROI 标注、环境诊断 | 测试识别 / 导出证据 |
| 设置 | 后端、游戏窗口、通知、主题、数据目录 | 保存 / 恢复默认 |

运行页建议采用四个稳定区域：

1. 顶部状态栏：后端连接、WebSocket、游戏窗口、当前运行状态。
2. 左侧任务区：任务和工作流列表、启用状态、最近运行结果。
3. 中央工作区：当前步骤、进度、主操作、配置摘要、运行时间线。
4. 右侧证据区：最新截图、关键日志、错误原因、可执行的恢复操作。

当前 GUI 中已有的“调度预览、运行快照、关键日志”卡片可以保留，但应与统一运行快照和事件时间线绑定，避免成为各自独立的展示逻辑。

### 5.6 GUI 视觉与交互规则

- 延续当前深色高对比工作台风格，使用颜色表达状态而不是装饰；成功、警告、错误和运行中状态应有固定语义。
- 每个页面只保留一个主操作，危险操作使用确认；暂停、恢复、停止等次级操作按运行状态动态显示。
- 长任务不使用持续遮挡主界面的全屏弹窗；进度固定在运行工作区，通知以抽屉或轻量提示呈现。
- 重要状态同时使用文字、图标和颜色，不依赖颜色单独传达信息。
- 日志默认展示摘要，允许展开上下文、截图和识别详情；避免一打开页面就被大量原始日志淹没。
- 配置字段要显示说明、默认值、范围、单位和是否会在运行中生效；保存时记录配置快照。
- 断线重连后先拉取运行快照，再接收增量事件，避免页面出现“看似空闲但后台仍在运行”的误导。

## 6. 分阶段改进路线

### P0：运行可靠性与可观察性

目标：让用户知道系统正在做什么、为什么失败、失败后能怎么处理。

建议内容：

- 定义连接、运行、步骤、动作四层状态枚举。
- 统一运行快照和 WebSocket 事件结构。
- 给运行实例补充 run_id、步骤 ID、错误码和可用操作。
- 为失败保存最近截图、配置快照和关键日志。
- 在工作流中实现 retry、skip、stop、manual 基础策略。
- GUI 运行页把当前步骤、状态、进度和失败操作放在首屏。

验收标准：

- 任务失败后，用户无需查看源码即可判断失败步骤和建议操作。
- 刷新或重连 GUI 后，能够恢复当前运行快照。
- 每次失败至少能定位到一张关联截图和一段关联日志。
- 未实现的失败策略不会在界面上伪装成已经生效。

### P1：任务工作台与调度体验

目标：让用户可以稳定配置、编排和重复运行任务。

建议内容：

- 把任务注册信息扩展为配置字段元数据：类型、默认值、范围、说明、敏感性。
- 将现有 GUI 右侧卡片、工作流弹窗和脚本列表收敛为可复用组件。
- 增加工作流编辑页和步骤级失败策略。
- 实现周期调度的最小闭环：启用、下一次运行、优先级、成功/失败间隔。
- 增加历史运行列表和详情页。
- 为前端增加 lint、类型检查和基础组件测试。

验收标准：

- 新增一个脚本任务时，不需要复制整页 HTML 才能展示配置和运行状态。
- 用户可以从历史记录直接查看一次运行的配置、步骤、日志和截图。
- 调度预览与实际运行时间一致；若存在限制，页面明确标注。
- 任务运行期间切换页面不会丢失控制入口和状态。

### P2：诊断工具与高级体验

目标：缩短识别问题的定位时间，提高新任务开发和维护效率。

建议内容：

- 增加截图、OCR 和图像定位的回放工具。
- 支持 ROI 标注、识别置信度和候选区域可视化。
- 提供一次运行证据包导出，包含配置、事件、日志、截图和版本信息。
- 为重复失败生成统计：错误码、任务、步骤、平均耗时和最近截图。
- 增加通知渠道和可配置的人工接管策略。

验收标准：

- 开发者可以使用离线截图重放核心识别步骤，不依赖实时游戏窗口。
- 用户可以将一次失败运行完整导出并交给他人复现或分析。
- 统计信息能够区分“脚本逻辑失败”“识别失败”“连接失败”和“用户停止”。

## 8. 研究限制与验证记录

### 8.1 研究限制

- 结论基于公开仓库 README、源码和当前可见的 GUI/后端结构，未覆盖外部项目全部运行环境和线上行为。
- 外部仓库可能持续变化；本文记录的是本次研究日期的观察结果，后续实现前应重新核对关键接口。
- 本文只提出目标设计与借鉴点，没有宣称 P0/P1 已经实现。
- 外部项目的许可证、资源授权和再分发条款应在实际复用代码或素材前单独审核。

### 8.2 本地验证记录

本次文档编写前已检查目标项目的以下内容：

- gui/index.html：确认当前已有执行、工作流、进度/日志/设置导航，以及调度预览、运行快照和关键日志区域。
- gui/renderer.js：确认当前采用全局状态、API 辅助函数、模板渲染和 WebSocket 事件处理，组件边界仍较弱。
